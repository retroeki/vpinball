# vpinball Rendering Performance Report — Vulkan & OpenGL (bgfx)

## Executive Summary

The highest-leverage wins fall into three classes, and they are not where micro-optimization instinct points. **CPU-submission**: the single biggest lever is the per-draw uniform storm — bgfx's OpenGL/GLES/Vulkan backends have the memcmp early-out deliberately bypassed (`Shader.cpp:1000-1005`), so every technique uniform is re-pushed on every one of thousands of draws; this fork already ships the fix primitive (`UniformFreq::View/Frame` + `setViewUniform`/`setFrameUniform`), making frame/view-constant matrices and post uniforms a once-per-view upload instead of O(draws). **GPU/bandwidth**: the dominant mobile costs are uncompressed textures on the bgfx path (no ASTC/ETC2 branch exists at all — `Sampler.cpp:40-50`), an unconditional `BGFX_TEXTURE_BLIT_DST` on every write-only RT that blocks UBWC/AFBC compression (`RenderTarget.cpp:131-133`), the 64bpp RGBA16F scene/PP surfaces that could be 32bpp R11G11B10F, and unnecessary tile LOADs on full-overwrite post passes that never set a clear/discard. **Sync/pacing**: the synchronous double-`SubmitRenderFrame` texture upload (`RenderDevice.cpp:2143-2144`) stalls the logic thread for two render-thread round-trips with a `Sleep(0)` spin, and the Android backend defaults to GLES while the team's Vulkan tuning lies dormant (`Settings_properties.inl:123`). Note throughout that **bgfx's abstraction caps several Vulkan-only ideas** — no subpass/input-attachment fusion, no attachment-based VRS, no memoryless/transient attachments, no per-draw uniform persistence — and these ceilings are flagged inline so effort is not wasted chasing them.

## By Subsystem

### Frame Graph (`SortPasses` / `RenderFrame` / `RenderPass`)

**O(n²)–O(n³) linear scans in `SortPasses`** — `bgfx-all`. *Today:* `SortPasses` (`RenderFrame.cpp:59-133`) uses `FindIndexOf` (a linear `std::find`, `def.h:177-185`) inside nested loops — the find-first-consumer scan (`78-80`), the backward-slide loop calling it twice per step (`91-92`), the constraint-propagation walk to end (`106-117`); `m_referencedRT` grows via insert-at-front (`103`); `AddPrecursor` scans linearly (`RenderPass.cpp:49-54`). *Change:* stable per-pass integer index, bitset/flat_set membership tests, cache min-consumer position, produce topo order via Kahn's algorithm. *Mechanism:* pure submit-thread CPU. *Impact: low / Effort: medium / Risk: medium.* The "already-inserted" test is actually O(1) via `m_sortKey` (`72-75`), so it is quadratic not cubic, and pass counts are tens even on heavy frames — so this is microseconds. Valid on any backend but low-priority.

**Non-maximal pass merging leaves redundant RT binds** — `bgfx-all`. *Today:* the merge step (`RenderFrame.cpp:120-132`) only fuses `pass[i]`/`pass[i+1]` when strictly adjacent + same RT + `m_mergeable`; the slide heuristic (`83-101`) bails on any dependency/`m_referencedRT` conflict (`91-96`), so the `[RT-A][RT-B][RT-A]` non-adjacent pattern never merges. Each unmerged same-RT boundary is a fresh `Activate()→NextView()` view (`RenderTarget.cpp:650-666`, `RenderDevice.h:256-269`). *Change:* a second consolidation pass pulling all mergeable passes of an RT together to the latest legal position. *Mechanism:* each extra view on a tiler is a potential tile load+store; on desktop Vulkan it is render-pass begin/end churn. *Impact: medium / Effort: large / Risk: high.* Important caveats: the slide heuristic already collapses the common case; `NextView` forces `setViewClear(BGFX_CLEAR_NONE)` and `RC_CLEAR` is hoisted to front by `SortCommands` (`RenderPass.cpp:95-99`), so fully-clearing passes already hit clear-on-load and skip the LOAD; and `Activate` already early-returns on unchanged RT+layer (`RenderTarget.cpp:652-653`), so the proposal's "skip NextView for same FB" sub-idea is already handled. The real win is the bounded non-adjacent case, and a bad reorder corrupts dependencies.

**Full-clear discard drops commands but never prunes dead producers** — `bgfx-all`. *Today:* `RenderPass::Submit()` (`RenderPass.cpp:170-180`) detects a full clear (`IsFullClear`, `RenderCommand.cpp:26-34`) and deletes prior commands of that pass, but an explicit TODO at `RenderPass.cpp:177` means it does **not** drop dependency edges to producers whose only output is the clobbered RT — so those producers survive `SortPasses` and execute on the GPU producing discarded pixels. *Change:* on full clear, drop `m_dependencies` edges to producers with no other live consumer, or invalidate `rt->m_lastRenderPass` so `SetRenderTarget`'s precursor inheritance (`RenderDevice.cpp:2421-2427`) does not re-link them. *Mechanism:* removes whole dead passes (draws + tile load/store). *Impact: low / Effort: medium / Risk: high.* Must respect `HasDepth`/shared depth (a TARGET-only clear must not prune depth producers). In practice the orphaned-producer pattern is rare — probe clears (`RenderProbe.cpp:333,349,403`) clear at the start of their own pass before producers wire in — so narrow.

**Area-of-interest scissoring does not shrink tiler load/store** — `bgfx-all`. *Today:* AOI passes (reflection/refraction blur `RenderProbe.cpp:179-189`, bloom blur `Renderer.cpp:1422-1426`) call `bgfx::setViewScissor` (`RenderPass.cpp:243-244`), but `Activate` still binds the full RT via `setViewRect(0,0,w,h)` (`RenderTarget.cpp:664-665`), so the tile load/store covers the whole grid even when only a sub-rect is touched. *Change:* also call `bgfx::setViewRect` to the AOI rect so binning/resolve only touch overlapping tiles; right-size the blur ping-pong RTs. *Mechanism:* tiler load/store cost is proportional to view-rect tiles, not scissor. *Impact: medium / Effort: medium / Risk: medium.* Tiler-specific and real for localized effects, but fiddly: narrowing `setViewRect` changes the viewport transform, so the static `m_quadMeshBuffer` NDC quad and UVs must be recomputed for the sub-rect or it mis-samples.

**Final-pass back-buffer precursor wiring is an O(N) rescan every frame** — `bgfx-all`. *Today:* before sorting, `Execute` scans all `m_passes` and calls `lastPass->AddPrecursor(pass)` (linear dedup, `RenderPass.cpp:52`) for every non-last back-buffer pass (`RenderFrame.cpp:187-189`), rebuilt from scratch each frame. *Change:* track back-buffer passes in a dedicated list at `SetRenderTarget` time, or mark them with a keep-flag consumed directly by `SortPasses` rather than synthetic edges that distort the slide heuristic (`91-96`). *Mechanism:* pure submit-thread CPU. *Impact: low / Effort: small / Risk: low.* Clean low-value cleanup.

**Refraction screen-copy split duplicates and re-sorts the producing pass** — `bgfx-all`. *Today:* command-level dependencies (`RenderFrame.cpp:191-212`) split the current pass and re-sort the subgraph via nested `SortPasses` with `vector::insert` at arbitrary positions; the FIXME at `RenderFrame.cpp:185` ("use list since we are populating through insertions") confirms the container is wrong for mid-sequence inserts. *Change:* switch `sortedPasses` from vector to list (or defer to a final flatten). *Mechanism:* removes O(N) shifts per insert. *Impact: low / Effort: medium / Risk: medium.* The proposal's other halves are already done: the screen-copy RT **is** cached across frames (`RenderProbe.cpp:238`, `if (m_dynamicRT == nullptr)`), and the split is already gated on an actual refracting command (`m_dependency != nullptr`, `primitive.cpp:1436`). Only the vector→list lever remains.

> **Duplicate merge note:** The "per-command transient quad VB" idea appears under *frame graph*, *draw batching*, *RT/bandwidth*, *threading/pacing*, *native-GL*, and *mobile-tiler*. It is consolidated in **Draw Batching** below.

### Draw Batching

**Eliminate the double full-uniform-blob `CopyTo` per draw** — `bgfx-all`. *Today:* each `DrawMesh`/`DrawTexturedQuad` does `CopyTo(true,...)` at record time (`RenderCommand.cpp:422,437,452`) and `CopyTo(false,...)` at Execute (`RenderCommand.cpp:136`), copying the whole `vector<uint8_t> m_state` plus the `m_samplers` shared_ptr vector both directions (`Shader.h:684-685`). *Change:* pass `ShaderState*` into `Begin()` so `ApplyUniform` reads the command snapshot directly, removing the Execute-time copy; store samplers by raw handle to avoid atomic refcount round-trips. *Mechanism:* per-draw CPU/memcpy + ARM atomic contention. *Impact: low / Effort: medium / Risk: medium.* `m_state` is one technique's uniform set (hundreds of bytes), not the whole shader, and the per-draw setUniform storm dwarfs this copy — so real but minor. **This is the same change as "Eliminate the per-draw full ShaderState CopyTo before Begin()" in Shaders/Uniforms (rated medium there); treat as one work item.**

**Re-enable uniform diffing or move shared uniforms to per-pass upload** — `vulkan`/both. *Today:* the memcmp early-out is bypassed for OpenGL/GLES/Vulkan (`Shader.cpp:1000-1005`), so `Begin()` (`Shader.cpp:699-700`) re-pushes every technique uniform per draw — `matView`/`matProj`, the `MAX_LIGHT_SOURCES` light arrays (`ball.cpp:378-381`), etc. *Change:* group frame/pass-constant uniforms and upload once per view, cutting the per-draw list to per-object uniforms. *Mechanism:* `bgfx::setUniform` copies into the command buffer each call; ~20-40 uniforms × ~1000 draws = tens of thousands of redundant stages/frame. *Impact: **high** / Effort: large / Risk: high.* The strongest CPU finding on the mobile target. **The "restore the memcmp early-out" half is unverified and high-risk** — the bypass is a deliberate correctness workaround; re-enabling it without proving bgfx now persists per-view uniform state would reintroduce stale-uniform rendering. The safe path is the `UniformFreq` refactor (see Shaders/Uniforms #1), with which this fully merges.

**Instance the balls (and reflections/trails) into a single draw** — `bgfx-all`. *Today:* each ball is its own `DrawMesh` of the shared `m_ballMeshBuffer` (`ball.cpp:466`), reflections/trails per-ball (`ball.cpp:306,500,593`); no `setInstanceDataBuffer`/`allocInstanceDataBuffer` exists anywhere — `nInstances` is the RT layer count for stereo (`RenderPass.cpp:250`→`RenderCommand.cpp:150,240,276`). *Change:* build a per-frame `allocInstanceDataBuffer` of per-ball world matrices and submit once. *Mechanism:* pure draw-call reduction. *Impact: low / Effort: large / Risk: medium.* Ball count is 1-6, so ≤5 draws saved. **Critical blocker:** the stereo path already consumes `setInstanceCount` for layer replication — you cannot use instancing for both layers and distinct balls without restructuring layered rendering (instance index would encode `layer*ballCount`); the deferred per-ball `SetMatrix` via `AddBeginOfFrameCmd` (`ball.cpp:474-483`) also breaks. The "validates plumbing for flasher/light instancing" rationale fails too — flashers/lights are not shared-mesh (`flasher.cpp:1290`, `light.cpp:802`).

**Transparent-pass secondary sort key for additive draws** — `bgfx-all`. *Today:* transparent draws sort **only** back-to-front by depth with no tiebreak (`RenderPass.cpp:114-126`), unlike the opaque key (technique→depth→meshbuffer→state, `136-162`); flashers/lights/lightmaps/trails thrash programs at close depth. *Change:* tag order-independent additive draws and add a technique/state secondary key within equal-depth groups. *Mechanism:* cuts program/PSO rebinds in the most state-churny pass. *Impact: low / Effort: medium / Risk: high.* **The core premise is largely wrong:** bulb lights use `DESTBLEND=INVSRC_COLOR` + `BLENDOP_REVSUBTRACT` + a modulate-vs-add factor (`light.cpp:790-798`) — order-*dependent*; lightmaps/flashers/trails use SRC_ALPHA over-blend (`ball.cpp:588-591`) — also order-dependent. The safely-reorderable subset is small and mis-tagging causes visible artifacts.

**Merge static-geometry meshes sharing shader+material** — `bgfx-all`. *Today:* `SortCommands` makes same-buffer opaque draws adjacent (`RenderPass.cpp:151-158`) but they stay separate submits; `VertexBuffer.cpp:185-198` already coalesces static parts into shared ≤65535-vertex buffers, and `MeshBuffer.cpp:25-26` folds VB offset into the IB. *Change:* at table-load, pre-merge index ranges of same-technique+material+texture static parts into one `DrawMesh`. *Mechanism:* collapses N submits to 1 (records, CopyTo, Begin, buffer binds). *Impact: medium / Effort: large / Risk: medium.* **Conditional:** VPX already renders unchanging opaque geometry once into a cached static-prepass RT (`RenderPass.cpp:66-69`), so eligible inserts/plastics/posts are largely *not* re-submitted per frame; the big win only materializes where the static prepass is disabled (reflections, dynamic shadows). Candidates also narrow to parts truly sharing material+transform.

**One transient quad VB per frame (consolidated duplicate)** — `bgfx-all`/`native-gl`. *Today:* `RC_DRAW_QUAD_PT`/`PNT` call `allocTransientVertexBuffer` for 4 verts + memcpy per command (`RenderCommand.cpp:146,184`, literal TODO "only allocate one per frame"); `RenderTarget::CopyTo` mirror blit duplicates it (`RenderTarget.cpp:600-602`); native-GL Lock/memcpy/Unlock the shared `m_quadPTDynMeshBuffer` per command (`RenderCommand.cpp:156-159`). *Change:* allocate one per-frame transient buffer and sub-allocate 4-vert slices with `startVertex`. *Mechanism:* removes per-command allocator bumps/memcpys on the submit thread. *Impact: low / Effort: small / Risk: low.* **Major caveat / merge note:** the headline "extend the static fullscreen quad to PP/blur paths" is **already done** — `DrawFullscreenTexturedQuad` uses the static immutable `m_quadMeshBuffer` (`RenderDevice.cpp:2500-2505,1628`) and is the path for blur, tonemap, AA, SSR, bloom-composite, stereo. The transient `RC_DRAW_QUAD_PT/PNT` path is only used for **variable-geometry** quads (DMD segments, mirror/clip sub-rects, motion-blur quads `Renderer.cpp:1994-2000,2508-2518`) whose vertices genuinely differ per call — so a static unit-quad-plus-uniforms swap is **not** applicable there; only one-transient-per-frame sub-allocation is. This idea recurs identically under frame-graph, RT/bandwidth, threading/pacing, native-GL, and mobile-tiler; it is one low-value cleanup.

### State / PSO

**bgfx `RenderState::Apply` does zero state dedup** — `bgfx-all`. *Today:* the `ENABLE_BGFX` branch (`RenderState.cpp:124-164`) rebuilds the uint64 `bgfx_state` from scratch (10+ branches, 4 table lookups) and unconditionally writes `device->m_bgfxState`, with no XOR-diff against the active state (the diff path at `185-364` is DX9/GL-only). `m_curStateChanges` is near-dead for bgfx (only the all-backend depthBias branch at `368-387` feeds it). *Change:* cache `m_lastAppliedBgfxState`, early-out the recompute, memoize the 21-bit `m_state`→uint64 decode, and wire `m_curStateChanges` so the cost is measurable. *Mechanism:* per-draw ALU/branch. *Impact: low / Effort: small / Risk: low.* `setState` itself can't be removed (PT_* topology OR'd per primitive); only the decode is saved, which is cheap branch work. Main value is enabling measurement for the next two ideas. (One factual slip in the source note: line 371's `++` is in the all-backend depthBias block, not the DX9/GL block.)

**All views forced to `ViewMode::Sequential`** — `vulkan`. *Today:* `NextView` calls `setViewMode(...,Sequential)` for every view (`RenderDevice.h:266`), disabling bgfx's program/state sort; VPX does its own `SortCommands`. *Change:* split each pass's opaque prefix into a sort-key view, keep the transparent tail Sequential (views submit in id order). *Mechanism:* lets bgfx coalesce same-program runs into fewer `vkCmdBindPipeline`. *Impact: low / Effort: large / Risk: high.* bgfx's sort key is coarse (program/depth, not full 64-bit state), so it would not necessarily dedup VPX's distinct pipelines; the kicker/playfield/flasher-DMD ordering hacks (`RenderPass.cpp:101-133`) are encoded in submission order and would break. Speculative; needs the (currently-dead) state-change counter first. **This is the same observation as "Every view forces ViewMode::Sequential" under bgfx config — merge.**

**PSO-defining render state is the *last* sort tiebreaker** — `both`. *Today:* opaque order is depthbias-hack→technique→depth→meshbuffer→`m_state` (`RenderPass.cpp:128-162`), with a TODO at `138-142` to sort techniques by min-depth. Same-technique draws differing in blend/cull/colormask get separated by depth → pipeline rebinds. *Change:* sort `technique → m_state → depth` within the opaque group. *Mechanism:* each pipeline bound once per technique-group. *Impact: low / Effort: medium / Risk: medium.* Within one technique render state is usually identical (small population); reordering away from front-to-back sacrifices early-Z — and **Adreno is *not* a fully-deferred HSR architecture** (it relies on early-Z), so this could *increase* fragment work there. Needs the A/B the proposal admits is required.

**Depth bias is an unimplemented FIXME on bgfx** — `bgfx-all`. *Today:* `RenderState::Apply` (`368-387`) has `// FIXME implement depth bias for BGFX` (`373`) — a no-op, while GL/DX9 call `glPolygonOffset`/`D3DRS_DEPTHBIAS`. The engine compensates with the `>50000` depthbias submission-order hack (`RenderPass.cpp:130-133`). *Change:* fold a depth-bias offset into the projection via uniform/`setViewTransform` for biased draws. *Mechanism:* enabler — removing the hack unblocks state-coherent sorting. *Impact: low / Effort: medium / Risk: medium.* Primarily a correctness fix on the Android target. Note the `>50000` layering hack and the small polygon-offset `m_depthBias` are related but distinct, so "implementing depth bias removes the 50000 hack" is partly conflated.

**Per-command full Apply + uniform re-upload (bgfx persistence)** — `vulkan`. **Same root issue as Draw-Batch #2 and Shaders/Uniforms #1**, viewed from the state lens: `RenderCommand::Execute` per draw runs Apply → `CopyTo(false)` → `Begin()` → `ApplyUniform` for every uniform, with the diff bypassed for bgfx (`Shader.cpp:1000-1005`, `1018` bumps `m_curParameterChanges`). *Change:* lift frame/pass-invariant uniforms out of the per-draw loop. *Impact: medium / Effort: large / Risk: medium.* Note `SUT_DataBlock`/uniform-block is `assert(false) // Unsupported for BGFX` (`Shader.cpp:1023-1024`), so the "shared constant buffer" route is unavailable; the achievable path is per-view binding of invariants.

**Frame-start force-apply writes an invalid state** — `both`. *Today:* `RenderDevice.cpp:1640-1642` inverts `m_current_renderstate.m_state` to force the first Apply to touch everything — correct for DX9/GL XOR-diff, meaningless for bgfx (which ignores `m_current_renderstate`). *Change:* none standalone; a correctness guard *if* idea-1's dirty check is added (must seed/invalidate the bgfx cache). *Impact: low / Effort: small / Risk: low.*

**`BGFX_STATE_PT_*` topology multiplies pipeline variants** — `vulkan`. *Today:* topology bits are OR'd into `m_bgfxState` per draw (`RenderCommand.cpp:151,242-246,279-283`; `RenderTarget.cpp:605`); on Vulkan topology is part of the PSO (absent `VK_EXT_extended_dynamic_state`, which bgfx doesn't assume), but the sort key (`RenderPass.cpp:162`) excludes topology, so strip/list of the same technique interleave → extra pipeline binds. *Change:* add a coarse topology bucket to the opaque sort key. *Mechanism:* coalesces `vkCmdBindPipeline`. *Impact: low / Effort: small / Risk: low.* Most draws are TRI-LIST/STRIP and mixing within a technique is uncommon; irrelevant on GLES (topology is a draw arg). Cheap to add once the state-aware sort exists.

### Shaders / Uniforms

**① Re-enable the uniform diff cache via `UniformFreq::View`/`::Frame`** — `both`. *Today:* all uniforms are created at default `UniformFreq::Draw` (`Shader.cpp:561`), so the diff early-out is bypassed for GL/GLES/Vulkan (`Shader.cpp:1000-1005`) and `Begin()` re-pushes every technique uniform per draw. *Change:* this fork exposes `createUniformFreq` (`bgfx.h:3340`), `setViewUniform` (`bgfx.h:3817`), `setFrameUniform` (`bgfx.h:3834`), and `UniformFreq::{Draw,View,Frame}` (`bgfx.h:295-303`) — and the Vulkan backend already *consumes* them (`submitUniformCache` copies view/frame uniforms into the persistent `m_uniforms[]` once per view, `renderer_vk.cpp:9083-9091,9284`; per-draw commit reads the same array, `9788-9799`). Create `matProj`/`matProjInv` (`Shader.h:333-334`) and `matView` (`339`) as View-frequency, post uniforms (`Shader.h:420-425`) as Frame-frequency, set via `setViewUniform`/`setFrameUniform`; keep `matWorldViewProj` (per-object, count=2) at Draw. *Mechanism:* per-draw matrix re-push (2×Mat4 = 256B) across thousands of draws → O(views) or O(1). *Impact: **high** / Effort: large / Risk: high.* `setUniform` asserts `m_freq==Draw` (`bgfx_p.h:3796`), so migrated uniforms must move; requires `.sc` recompile awareness and validating per-draw descriptor reuse. **This is the canonical, backend-blessed form of Draw-Batch #2 and the bgfx-config uniform ideas — they all collapse into this.**

**② Hoist view/frame-constant uniforms out of the per-draw `Begin()` loop** — `bgfx-all`. Same goal as ①, "lite" form (a per-view "already applied" set on Draw-freq uniforms). *Impact: medium / Effort: medium / Risk: medium.* **Fragile as a standalone:** `setUniform` asserts `m_freq==Draw`, and the per-draw Vulkan commit rebuilds the program constant set from `m_uniforms[]` on program change (`renderer_vk.cpp:9788`); simply not re-pushing a Draw-freq uniform after a program switch leaves a stale value. Collapse into ① to be safe.

**③ Consult `m_boundState` as a real early-out after fixing persistence** — `both`. *Today:* `ApplyUniform` computes the memcmp against the global `GetUniformState()` (`Shader.cpp:982,998`) but discards the result for GL/GLES/Vulkan (`1000-1005`). *Change:* once persistence is guaranteed, drop those backends from the skip-list so equal uniforms are skipped. *Impact: medium / Effort: small / Risk: high.* The "just allow the return" framing understates the validation: it is gated entirely on ①'s persistence proof, and a wrong assumption produces stale-uniform corruption. (Note: on the bgfx path the diff target is the global `GetUniformState`, not `m_boundState` — that array is only the GL/DX9 diff target.)

**④ Pack scalar/bool/int/vec2/vec3 uniforms instead of full-vec4 pushes** — `bgfx-all`. *Today:* bgfx maps all scalar types to `Vec4` and each push expands to a full vec4 (`Shader.cpp:548-554,1040-1098`); several scalars listed per draw (`alphaTestValue`, `layer` at `RenderCommand.cpp:135`). *Change:* pack related scalars into one shared vec4 (the codebase already does this for `u_basic_shade_mode`, `Shader.cpp:856`). *Impact: low / Effort: medium / Risk: medium.* Each `setUniform` is one entry + 16B copy; the used-uniform list is already modest, the scalars to pack mostly belong to different techniques, and it **requires editing `.sc`/`.sh` sources** with silent wrong-component bugs on mismatch (high-risk per patcher fragility). Does nothing for matrices, which dominate. Marginal.

**⑤ Reduce clip-plane program/variant explosion** — `vulkan`. *Today:* clip-capable techniques compile two programs each (`m_techniques[]` + `m_clipPlaneTechniques[]`, `Shader.h:565-566`; `_noclip` then `_clip` for ~13 basics + ball, `Shader.cpp:1520-1564`), selected per draw by `GetCore()` (`Shader.cpp:1289-1291`). *Change:* the achievable, defensible part — **audit which techniques ever run with `CLIPPLANEENABLE=TRUE` (only reflection/refraction) and only compile clip variants for those**. *Mechanism:* fewer Vulkan PSO compiles at table load (an Adreno/Mali stutter source). *Impact: medium / Effort: large / Risk: high.* **The headline "fold clip into noclip via uniform branch / specialization constant" is partly invalid under bgfx** — bgfx does not expose Vulkan specialization constants through its high-level API, and a dynamic uniform branch costs ALU on mobile. Steady-state runtime benefit is small.

**⑥ Eliminate the per-draw full `CopyTo(false)` before `Begin()`** — `bgfx-all`. *Today:* per draw, `CopyTo(false, m_shaderState)` (`RenderCommand.cpp:136`) copies the full `m_state` vector + `m_samplers` flat_map back into live state, solely because `Begin()` reads `m_shader->m_state`; the only true per-draw mutation is `SHADER_layer` (`135`). *Change:* pass the captured `m_shaderState` into `Begin()`/`ApplyUniform`. *Mechanism:* removes a hundreds-of-bytes vector + flat_map copy per draw, host-side only (backend-independent). *Impact: medium / Effort: medium / Risk: medium.* Must read the captured snapshot, not mutated live state, since commands are recorded then sorted/replayed. **Same change as Draw-Batch #1.**

**⑦ Cache bound program to skip `GetCore()` per draw** — `bgfx-all`. *Today:* the bgfx path skips `m_boundTechnique`/`m_curTechniqueChanges` (`#if !ENABLE_BGFX`, `Shader.cpp:679-697`) and evaluates `GetCore()` per submit (`1286-1292`). *Change:* track last program + wire `m_curTechniqueChanges` for telemetry. *Impact: low / Effort: medium / Risk: low.* `GetCore()` is a cheap state-read + array index; bgfx already de-dups program binds at the backend (`renderer_vk.cpp:9788`), so host-side caching largely duplicates that. The genuinely useful sliver is the telemetry counter (a measurement aid, not a perf win).

### Textures

**Add GPU texture compression (ASTC/ETC2) on the bgfx path** — `bgfx-all`. *Today:* `m_compressTextures` (`Renderer.cpp:101`, `RenderDevice.cpp:1113`) is consulted **only** in the GL (`Sampler.cpp:586`, BC7/BC6S/DXT5) and DX9 (`Sampler.cpp:667`) branches; the bgfx path (`Sampler.cpp:40-50`, `UpdateTexture:410-473`, `GetCoreTexture:207-383`) never references it and always creates uncompressed RGBA8/16F/32F, uploading raw via `makeRef`. *Change:* when set and dims qualify, transcode LDR→ASTC4x4/6x6, HDR→BC6H, query `getCaps()->formats[...]`, fall back to RGBA8. bimg ships the encoder (`encode.h:30,56` — astc-encoder/etc1/squish), though `Sampler.cpp` only includes `decode.h`. *Mechanism:* 4-8× texture-fetch bandwidth and VRAM/eviction reduction on the fetch-bound tiler. *Impact: **high** / Effort: large / Risk: medium.* **Single biggest mobile texture lever — currently zero GPU compression on Android.** Caveats: CPU ASTC encode is slow and must be cached on disk / done off-thread or done **offline at import** (the app has an import pipeline); correct sRGB-vs-linear per `IsLinearFormat` (`Sampler.cpp:437`); compressed formats can't be compute-mipped, so generate mips before compression or via driver autogen. **This duplicates the mobile-tiler "ASTC" idea — one work item.**

### Post-Processing

**Fuse FXAA/NFAA + CAS sharpen into one pass** — `bgfx-all`. *Today:* AA (`Renderer.cpp:2541-2554`) and sharpen (`Renderer.cpp:2629-2651`) are two full-res passes via `m_FBShader`, both with the depth early-out, on RGBA8 PP RTs (`Renderer.cpp:495`). *Change:* a combined `FXAA_CAS` technique. *Impact: low / Effort: medium / Risk: medium.* **Correctness problem the proposal understates:** CAS sharpens the *post-AA* image using a 3×3 neighborhood of AA'd pixels, but a fused pass only has the AA result at the *center* texel — fusing requires recomputing FXAA at all 8 neighbors (8× the edge-walk) or sharpening raw pre-AA neighbors (not equivalent, degrades quality). **Android defaults to GLES, never Vulkan** — `vulkan`. *Today:* `GfxBackend` defaults to `"OpenGLES"` (`Settings_properties.inl:123`); even `"Default"` picks GLES because bgfx's scoring (`bgfx.cpp:2827-2834`) gives OpenGLES +20 on Android and Vulkan 0; `m_useLowPrecision` is forced regardless (`RenderDevice.cpp:1176`). *Change:* benchmark Vulkan vs GLES on representative hardware; if Vulkan wins, default Android to Vulkan with a capability check + GLES fallback; surface the selected renderer (already PLOG'd at `1242`). *Mechanism:* Vulkan records into precompiled PSOs/command buffers, avoiding per-draw `glUseProgram`/`glBind*`/redundant-state CPU validation, with explicit load/store-op control on the tiler. *Impact: **high** / Effort: small (flag) / Risk: medium.* **Largest lever before micro-tuning — the tuned Vulkan path is dormant.** But the win is conditional on an unproven benchmark, and the GLES default may be a **deliberate stability choice** (documented Vulkan swapchain-teardown crash mitigations). Recommend benchmark-then-default-with-fallback, not a blind flip.

**Every view forces `ViewMode::Sequential`** — `bgfx-all`. **Duplicate of the State/PSO Sequential idea** (`RenderDevice.h:266`). *Impact: low / Effort: medium / Risk: high.* bgfx still records into one command stream regardless of view mode; sorted mode reorders but does not *merge* draws into fewer API calls; and it would discard the kicker/mask/playfield ordering constraints VPX encodes. Narrow opaque-prepass-view candidate only.

**Encoder / multi-threaded command recording unused** — `vulkan`. *Today:* all draws go through immediate `setVertexBuffer/setState/submit` on one thread (`RenderCommand.cpp:149-152,240-286`; `RenderFrame.cpp:245`); 8 encoder slots exist but are unused (`config.h:405-407`). *Change:* record independent passes on parallel `bgfx::Encoder`s behind a Vulkan-only flag; measure `PROFILE_RENDER_SUBMIT`. *Impact: low / Effort: large / Risk: high.* **Architecture-breaking:** conflicts with the deliberate single-thread `renderFrame()` model (`RenderDevice.cpp:736-743`) and the Android Surface park/teardown crash logic that assumes one presenting thread. Only helps if submit is actually CPU-bound (often false on mobile — GPU/bandwidth-bound). Speculative experiment with a profiling gate.

**`bgfx::getCaps()` dereferenced per-NextView / per-RT-activation** — `bgfx-all`. *Today:* `NextView` reads `getCaps()->limits.maxViews` twice per advance (`RenderDevice.h:258,260`), called from every `Activate` (`RenderTarget.cpp:659`) and mipmap gen (`Sampler.cpp:341`); `GetCoreTexture` reads `maxFrameBuffers`/`maxViews` per pending mip (`326-327`). *Change:* cache immutable caps into RenderDevice members after init. *Impact: low / Effort: small / Risk: very low.* Free overhead removal (caps fixed after init; HDR10 reset changes formats not limits), negligible FPS effect.

**`maxFrameLatency` defaults to 0 (unbounded draw-ahead)** — `bgfx-all`. **Same setting as the threading/pacing frames-in-flight item.** *Today:* default 0 (`Settings_properties.inl:113`, "Recommended to be left at 0"); the `Flip()` comment warns an unbounded queue lets the driver block on a later backbuffer-dependent draw, delaying input/physics and breaking PinMAME video modes (names Lethal Weapon 3, `RenderDevice.cpp:1981-1987`); VPX compensates with the CPU sleep loop (`1015-1037`). *Change:* default 1-2 on Android, A/B `PROFILE_RENDER_FLIP`, pair with existing pacing to avoid double-throttle. *Impact: medium / Effort: small / Risk: medium.* Corrections: the UI caps the setting at 0..5 (the 255 is only the init clamp ceiling); the existing CPU pacing already bounds queue growth in the synced case, so the risk is mostly latent for unsynced/over-refresh. Must be Android-scoped (desktop default-0 untouched).

**View 0/1 reserved for mipmaps; per-mip NextView pressures the 256-view budget** — `bgfx-all`. *Today:* rendering starts at view 1 with 0/1 reserved (`RenderDevice.h:273`); driver mip-gen consumes a `NextView` per pending texture (`Sampler.cpp:341`), deferred near `maxFrameBuffers-16`/`maxViews-32` (`325-328`); at `maxViews-1`, `NextView` force-submits and flips mid-frame (`258-263`) — a correctness hazard + perf cliff. Defaults: 256 views, 128 framebuffers (`config.h:250,305`). *Change:* batch per-frame mip-gen into a small fixed view range; optionally raise `BGFX_CONFIG_MAX_FRAME_BUFFERS`. *Impact: low / Effort: medium / Risk: low-medium.* Reaching the force-flip needs ~256 views in one frame — a defensive guard for heavy texture-streaming on load, not a steady-state cost. Raising `MAX_FRAME_BUFFERS` only relaxes the `-16` deferral, not the `-32` one. Gate work on confirming visible LOD pop-in.

### Native-GL (desktop only — **not the Android target**)

> All four items below are under `#elif defined(ENABLE_OPENGL)`. The Android/standalone build is unconditionally `ENABLE_BGFX` (`CMakeLists.txt:197`); there is no gl-android cmake. **These are desktop-GL-only wins — mobile relevance claims are rejected, since Android runs bgfx.**

**Stop re-uploading + re-binding the matrix UBO per draw** — `native-gl`. *Today:* `ApplyUniform` for `SUT_DataBlock` (basicMatrixBlock/ballMatrixBlock, `Shader.cpp:351-352,2031`) does `glBindBuffer` + `glBufferData(GL_STREAM_DRAW)` (orphan) + `glUniformBlockBinding` + `glBindBufferRange` per changed draw (`1026-1029`), and **even the unchanged branch still calls `glUniformBlockBinding` + `glBindBufferRange` every draw** (`1008-1013`). *Change:* set `glUniformBlockBinding` **once at link time** (`compileGLShader`, `2031`); use `glBufferSubData`/persistent-mapped UBO; track the bound range and skip redundant rebinds. *Mechanism:* `glBufferData` re-specifies UBO storage each draw (orphaning); `glUniformBlockBinding` can force program re-validation. *Impact: medium / Effort: medium / Risk: medium.* Real for the desktop GL build only.

**One transient quad VBO per frame instead of Lock/memcpy/Unlock per quad** — `native-gl`. *Today:* `RC_DRAW_QUAD_PT/PNT` do `Lock`(`new uint8_t[size]`, `IndexBuffer.h:51`)/memcpy/`Unlock`/bind/`glDrawArrays` per command, reusing one shared dynamic buffer that each draw stomps (`RenderCommand.cpp:154-163,192-201`). *Change:* per-frame ring buffer with base-vertex offsets. *Impact: low / Effort: medium / Risk: medium.* On the bgfx/Android target this is **already satisfied** by bgfx transients (no heap alloc, no `glBufferSubData`); the heap churn exists only in desktop GL.

**Skip redundant IB re-bind when the VAO is unchanged** — `native-gl`. *Today:* `MeshBuffer::bind()` unconditionally `m_ib->Bind()` (`glBindBuffer(GL_ELEMENT_ARRAY_BUFFER)`) for every indexed draw even for an already-bound VAO (`MeshBuffer.cpp:238-245`), with a comment that the author doesn't know why the VAO loses the IB binding. *Change:* root-cause the lost binding (likely a path binding `GL_ELEMENT_ARRAY_BUFFER` or VAO 0 outside `bind`), then guard behind `if (rd->m_curVAO != m_vao)`. *Impact: low / Effort: medium / Risk: medium.* **The workaround exists because removing it crashed Totan in camera mode (`242-243`) — must root-cause first** or the crash returns.

**Reconsider the unconditional per-frame `glFlush`** — `native-gl`. *Today:* `RenderFrame::Execute` issues one `glFlush()` per rendered frame before `SDL_GL_SwapWindow` (which implies a flush) (`RenderFrame.cpp:250-251`; `RenderDevice.cpp:2025`). *Change:* measure removing it / gate behind sync-mode. *Impact: low / Effort: small / Risk: medium.* At most one redundant call per *frame* — negligible ceiling; verify-first as it may perturb latency on specific drivers. (bgfx branch has no `glFlush`, so nothing to remove on Android.)

**Avoid the O(n) sampler-unit LRU age-loop per bind** — `native-gl`. *Today:* `ApplyUniform`'s GL path shifts the `m_samplerBindings` array (sized 16-32+, `RenderDevice.cpp:1397-1411`) to maintain LRU on **every** sampler apply (`Shader.cpp:1244-1250`). *Change:* intrusive move-to-front list (O(1)) or timestamp + victim-on-eviction. *Impact: low / Effort: medium / Risk: low.* **Correction:** there is **no** early return — when a texture is already bound (`1206-1213`) the code skips only the rebind block but still falls through to the LRU loop, so it runs on every apply. Still bounded by `use_rank` (front-hit ≈ no work); micro CPU on desktop GL only.

## Mobile Tiler (Adreno / Mali) Priorities

The engine ships on Android via bgfx-GLES (and potentially Vulkan). On a tile-based deferred renderer the binding constraint is **main-memory bandwidth** (tile load/store) and **CPU submit cost**, not raw ALU. Pulling the bandwidth/load-store/precision wins together, in rough leverage order:

1. **ASTC/ETC2 texture compression** (`Sampler.cpp:40-50`) — *high, large.* The single biggest pure-mobile lever; the bgfx path currently has **zero** GPU compression. 4-8× fetch-bandwidth and VRAM reduction; do the encode offline at import to avoid load-time regression. **Same as Textures #1.**

2. **Drop `BGFX_TEXTURE_BLIT_DST` from write-only RTs** (`RenderTarget.cpp:131-133`) — *medium, small.* Highest-leverage low-effort change; `TRANSFER_DST` blocks UBWC (Adreno) / AFBC (Mali) compression and transient allocation on every full-screen surface. **Caveat:** the AFBC/transient benefit is bgfx-and-driver-dependent.

3. **R11G11B10F for scene/reflection/motion-blur (64→32bpp)** (`Renderer.cpp:157`, `RenderTarget.cpp:138`) — *medium, medium.* Halves traffic on the most-trafficked surface. Requires a **new `colorFormat` enum entry + mappings** (`typedefs3D.h:108-147`) and must be **gated off when DLAA (alpha-FB, `Renderer.cpp:2559`) or HDR-alpha is used**. RGB10A2 is wrong for HDR.

4. **Explicit CLEAR-on-load for full-overwrite PP passes** (`RenderTarget.cpp:659`, `RenderCommand.cpp:55`) — *medium, medium.* Tonemap/sharpen/upscale/DLAA call `SetRenderTarget(...,false)` with no clear, so `NextView`'s default `BGFX_CLEAR_NONE` ⇒ `VK_ATTACHMENT_LOAD_OP_LOAD` (`renderer_vk.cpp:3672`) ⇒ an unnecessary tile LOAD of the whole RT. **Critical bgfx mechanism correction:** the fix is to emit an explicit **`BGFX_CLEAR_COLOR` (LOAD_OP_CLEAR)** for fully-overwritten passes — **not** the `BGFX_CLEAR_DISCARD_*` flags the proposal names, which map to *store-op* `DONT_CARE` / `glInvalidateFramebuffer` and control the **end-of-pass store**, not the load. There is no color `LOAD_OP_DONT_CARE` in bgfx. Risk: additive passes (SSR uses `SetRenderTarget(...,true)`, `Renderer.cpp:2036`) genuinely need prior content.

5. **Lower-precision PP intermediates (bloom RG11B10F; post-tonemap LDR RGBA8/RGB10A2)** (`Renderer.cpp:220`, `fs_pp_blur.sc:113`, `fs_pp_tonemap.sc` alpha=1.0) — *medium, medium.* Bloom never needs alpha or full FP16; post-tonemap LDR passes are in display range. Format choice must follow the HDR→LDR boundary (`tonemapRT` at `Renderer.cpp:3016`) or it clips HDR. **Overlaps the bloom-precision and scene-format ideas — ship the enum plumbing once.**

6. **mediump/fp16 precision in bandwidth/ALU-bound fragment shaders** (`RenderDevice.cpp:1176`, `Shader.h:725`, `common.sh:7`) — *medium, large.* `m_useLowPrecision` only clamps CPU-side uniforms to fp16 min-normal (2⁻¹⁴) — the **intent to run mediump exists but shaders still execute fp32**. Adreno/Mali run fp16 at up to 2× rate with half the register file. Apply surgically (blur accumulators, tap results, weights, LDR color) and keep highp for positions/depth/matrices/luminance; banding risk + the project's known approx-math divergence demand on-device A/B.

7. **Half-res SSAO/SSR; resolution-scaled bloom kernel; NFAA default; sample-count caps** — *medium-low.* Quarter the invocations and cache-hostile depth/color fetches of the heaviest fragment passes; NFAA removes the divergent edge-walk. (Post-processing section; several still `unverified` — re-ground before implementing.)

8. **Async texture upload** (`RenderDevice.cpp:2143-2144`) — *medium.* Removes the logic-thread `Sleep(0)` core-spin (thermal/battery on phones) and the two-round-trip stall during table load and DMD/video streaming.

### bgfx Abstraction Ceilings (do not chase these within bgfx)

The most powerful tiler optimizations are **unreachable from this codebase** because bgfx hides them:

- **No subpass / input-attachment fusion.** The separable bloom H-then-V blur must round-trip the 1/4-res buffer through main memory because bgfx exposes no Vulkan subpass or GLES PLS/framebuffer-fetch API. On-chip blur fusion requires a native-Vulkan escape hatch. Only resolution/format reductions are available within bgfx. *(unverified item, but the limitation is structural.)*
- **No memoryless/transient attachments.** The bgfx-Vulkan backend creates every image with `TRANSFER_SRC|TRANSFER_DST|SAMPLED` and binds real device memory (`renderer_vk.cpp:6459-6502`) — **no `VK_IMAGE_USAGE_TRANSIENT_ATTACHMENT` / `LAZILY_ALLOCATED` anywhere.** `BGFX_TEXTURE_RT_WRITE_ONLY` only lets the renderpass set depth `storeOp=DONT_CARE` and skip a layout barrier; it never makes an attachment memoryless. So the "memoryless write-only depth" idea (`RenderTarget.cpp:133`) is **not achievable** — the realistic saving is eliding the depth *store* via `storeOp=DONT_CARE` when depth is unsampled downstream, which is gated on dropping the tonemap depth early-out (a behavior change, not a free win).
- **No attachment-based VRS** for the VR fragment-shading-rate path (above).
- **No per-draw uniform persistence** on GL/GLES/Vulkan — the entire uniform-storm class of fixes hinges on this fork's `UniformFreq` extension, which is the *only* sanctioned way to make per-view/frame uniforms stick.

## Recommended Sequencing

1. **Instrument first.** Wire `m_curStateChanges`/`m_curTechniqueChanges`/`m_curParameterChanges` on the bgfx path (State/PSO #1, Shaders #7) — several medium/high ideas (Sequential split, state-coherent sort) are explicitly gated on measurement that is currently dead for bgfx.
2. **Ship the two cheap structural tiler wins:** drop `BGFX_TEXTURE_BLIT_DST` (small) and add the R11G11B10F enum+mapping plumbing (medium) that unblocks scene-format, bloom-format, and PP-LDR ideas together.
3. **Land the uniform-frequency refactor** (Shaders #1) behind validation — the single highest CPU lever, and it subsumes Draw-Batch #2, Shaders #2/#3, and the state/config uniform items.
4. **Add ASTC compression at import** (Textures #1) — highest GPU-bandwidth lever, large but offline-amortizable.
5. **Benchmark Vulkan-vs-GLES on Android** (Config #1) before any further backend-specific tuning, with the GLES-fallback safety net intact given the known swapchain-teardown crash history.
6. Async texture upload (#8) and the explicit-CLEAR PP pass (#4) as follow-ons.

Treat every `unverified` post-processing item as needing a re-grounding pass against current source before implementation, and treat all `native-gl` items as desktop-only.
